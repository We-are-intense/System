## 核心观点

### 1. 一切都是状态机

| 层次 | 状态 | 初始状态 | 状态迁移 |
|---|---|---|---|
| 汇编 / 机器指令 | 内存 M 加寄存器 R | 由 ABI 规定（例如 `%rsp` 指向合法的栈） | 执行一条指令 |
| C 程序 | 栈帧列表加全局变量 | 只有 `main(argc, argv)` 这一个栈帧，全局变量取初值 | 执行栈顶帧 PC 处的一小步语句 |

C 程序状态机里的函数调用和返回：

- **函数调用 = push 一个栈帧**（新帧的 PC 指向函数入口）
- **函数返回 = pop 一个栈帧**

这就是为什么递归总能改写成"显式栈加循环"。课上用非递归汉诺塔演示了这一点：自己维护一个栈，每个元素就是一个"栈帧"（n、from、to、via 加上当前执行到哪一步）。

> 我的理解：只要"状态 + 迁移"定义清楚，就可以写一个解释器去执行它，gdb 的单步执行就是这么回事。后面的线程（多个栈）、进程（多个地址空间）、上下文切换（保存和恢复一个状态机的状态），都建立在这个模型上。

### 2. 程序为什么停不下来：系统调用

实验：不用 libc，手写一个最小程序，直接用 `ld` 链接。

- `while (1);` 可以正常运行，永远不退出。
- 写一个直接 `return` 的 `_start`，结果 **Segmentation Fault**：`_start` 不是被谁调用的函数，栈上没有合法的返回地址可以 `ret`。
- 关键结论：**纯计算的状态机没有"停机"指令**。想停下来，只能请操作系统帮忙。

```asm
# x86-64 Linux：exit(1)
movq $60, %rax    # SYS_exit
movq $1,  %rdi    # status = 1
syscall           # 把整个 (M, R) 交给操作系统
```

指令可以分成三类：

| 类型 | 例子 | 性质 |
|---|---|---|
| 确定性计算 | `mov` `add` `call` | 同样的状态，执行结果永远一样 |
| 非确定性计算 | `rdrand`（硬件随机数） | 结果不确定 |
| **系统调用** | `syscall` | 把状态机的控制权完全交给操作系统；操作系统可以读写程序的状态，也可以直接终止它 |

**应用程序和操作系统沟通的唯一桥梁就是系统调用指令。** 从程序的视角看，执行 syscall 就像"打了麻药"：醒来时世界变了（例如 `read` 读进来了数据），但它感受不到时间流逝。操作系统给每个程序制造了"独占整台计算机、逐条执行指令"的假象。

### 3. 编译器：两个状态机之间的翻译

编译器把 `.c` 状态机翻译成 `.s` 状态机。怎样的翻译才算"正确"？

**`.c` 执行过程中所有外部可观测的行为，在 `.s` 里必须保持一致。** 外部可观测的行为包括：

- 对外部函数的调用（调用约定由 ABI 规定），其中包括系统调用，所以这些调用**不能删除，也不能交换顺序**
- `volatile` 读写、内联汇编（编译器提供的"不许优化"标注）
- 是否终止：`.c` 终止，当且仅当 `.s` 终止

只要满足这几条，编译器怎么改写都合法。这就是优化的空间，也是 compiler barrier 存在的原因。

> 我的理解：这是后面"并发"部分的伏笔。多线程程序里，另一个线程读写同一块内存，也算"外部观测者"，但编译器并不知道它的存在。所以才需要 `volatile`、内存屏障和原子操作。iOS 上 `os_unfair_lock` 和 `atomic` 背后也是这个问题。

### 4. 操作系统上的任何程序

**任何程序 = 一个会调用 syscall 的状态机。** 它的一生：

1. 另一个进程执行 `execve`，操作系统加载它，并设置好初始状态
2. 状态机开始执行，期间不断通过系统调用和操作系统交互：
   - 进程管理：`fork` `execve` `exit`
   - 文件 / 设备：`open` `read` `write` `close`
   - 内存：`mmap` `brk`
3. 调用 `_exit`（实际是 `exit_group`）退出

可执行文件本身也只是操作系统里的一个普通文件对象，以 `\x7fELF` 开头，可以用 `xxd` 直接查看。

浏览器、编辑器、杀毒软件，也都是建立在这些 API 和操作系统对象之上的：

| 程序 | 主要依赖的系统调用 / 对象 |
|---|---|
| gcc | `execve`（会启动多个子进程）、`read`、`write` |
| 图形界面编辑器（X11） | `poll`、`recvmsg`、`writev`（按 X11 协议和 X server 通信） |
| 任务管理器 | 读 `/proc` 下的进程对象（`readdir`、`read`） |
| 杀毒软件 | 静态扫描文件（`read`），主动防御（`ptrace`） |

### 5. 观察状态机的三类工具

理解程序的根本方法，就是**用合适的方式观察状态机的执行**。贯穿整门课的三类工具：

- **调试器**（gdb）：看任意时刻的状态，单步迁移。`starti` 可以从第一条指令开始跟踪
- **trace**（strace）：看程序和操作系统的边界，也就是系统调用序列
- **profiler**：看时间都花在哪里

## 对照：iOS / macOS 上的同一件事

| Linux 课上讲的 | macOS / iOS 上的对应 |
|---|---|
| `syscall` 指令（x86-64） | arm64 上是 `svc #0x80`，系统调用号放在 `x16` |
| ELF（`\x7fELF`） | Mach-O（魔数 `0xfeedfacf`） |
| `strace` | `dtruss` / `dtrace`（需要关闭 SIP），Instruments 的 System Trace |
| `/proc` | 没有 procfs，用 `sysctl` 和 `proc_pidinfo` |
| `execve` 后由 ld.so 做动态链接 | `execve` 后由 dyld 加载 |

## 和 xv6 的连接

- xv6 的 `user/usys.pl` 会生成每个系统调用的用户态桩代码：把系统调用号放进 `a7`，然后执行 `ecall`。这就是 RISC-V 版的"`movq $SYS_exit, %rax; syscall`"。
- xv6 的 `user/initcode.S` 就是一个"最小程序"：它是第一个用户进程，只做一件事，调用 `exec("/init")`。
