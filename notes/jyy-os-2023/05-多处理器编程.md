## 这一讲回答的问题

1. 线程是什么？怎样用最简单的 API 写多线程程序？
2. 写顺序程序时默认成立的哪些假设，到了多处理器上不再成立？

## 核心观点

### 1. 并发从哪里来

第 4 讲的模型里，操作系统是"状态机的管理者"：执行 `sys_sched()` 之后，它可以随意挑一个状态机来执行。**并发就是这样产生的。操作系统是世界上最早的并发程序。**

**线程 = 共享内存的执行流。** 每个线程有自己独立的栈和寄存器，但堆和全局变量是共享的。

课上用一个极简的 `thread.h` 封装了 pthreads：

- `create(fn)`：创建一个从 `fn` 开始执行的线程
- `join()`：等待所有线程结束

两个线程分别不停地打印 `a` 和 `b`，CPU 使用率就会超过 100%：操作系统自动把它们放到了不同的处理器上，真正在并行执行。

值得自己追问的问题："线程真的共享内存吗？怎样证明？""每个线程的栈有多大，范围在哪里？"课上的 `stack-probe` 示例就是用来回答后一个问题的。

### 2. 放弃 (1)：原子性

写顺序程序时，我们默认"世界上只有我一个状态机"，所以对一个变量的读取，一定返回本线程最后一次写入的值。编译优化也建立在这个假设之上。**共享内存推翻了这个假设：别的线程随时可能修改它。**

**经典例子："山寨支付宝"**

```c
if (balance >= amt) {   // 两个线程同时通过了检查
    balance -= amt;     // 然后各扣一次，余额下溢成一个巨大的正数
}
```

"检查"和"修改"之间可能插进别的线程。现实中真有类似漏洞造成巨额损失的事故，比如 Mt. Gox 交易所。

**例子：两个线程各执行 n 次 `sum++`**，结果几乎总是小于 2n，甚至可能小于 n。`sum++` 实际上是"读 → 加一 → 写回"三步，两个线程交错执行时，一方的写入会覆盖另一方的。

> **本机实测**（Apple M4，clang `-O0`，n = 1 亿）：`sum = 100042942`，期望 200000000，丢了将近一半。

单处理器上，线程可能在任意两条指令之间被中断切走；多处理器上，线程干脆就是真正同时在执行。**"一次执行一条指令"的假设不再成立。**

推论：`printf` 内部有缓冲区，类似 `buf[pos++] = ch` 这样的操作在多线程下必然出问题，那为什么多线程程序里还能放心用 `printf`？因为 libc 内部加了锁（`man 3 printf` 里能查到它是线程安全的）。

### 3. 放弃 (2)：执行顺序

编译器默认只有一个线程在访问内存，因此会随意合并、删除、调换内存访问：

| 优化级别 | 编译器把循环里的 `sum++` 变成了 | 两个线程的结果 |
|---|---|---|
| `-O1`（课上的 gcc） | 读一次 `sum` 到寄存器，加 n，最后写回一次 | 恰好 n，另一个线程的工作全被覆盖 |
| `-O2`（课上的 gcc） | 直接 `sum += n` | 2n，看起来"正确"了 |

> **本机实测**（clang）：`-O1` 和 `-O2` 都得到 200000000。**结果"正确"不代表程序正确**：clang 把循环合并成了一次加法，竞争窗口变得极小，但 data race 依然存在。

另一个经典陷阱：

```c
while (!done) ;          // 等另一个线程把 done 置 1
// 可能被优化成：
if (!done) while (1) ;   // 只读一次 done，然后永远死循环
```

**让编译器不要乱动的两种方法：**

- 插入 **compiler barrier**：`asm volatile ("" ::: "memory");`，告诉编译器"内存可能被改了，之前缓存在寄存器里的值都作废"
- 把变量标成 **`volatile`**：每次读写都必须真实地访问内存

回想第 2 讲的"编译正确性"：只有外部可观测的行为不能改变。而编译器根本不知道另一个线程也是"观测者"。

### 4. 放弃 (3)：处理器间的即时可见性

就算编译器老老实实按顺序生成指令，**处理器本身也会乱序执行**。

**store-load 例子：**

```c
int x = 0, y = 0;
T1:  x = 1;  t1 = y;
T2:  y = 1;  t2 = x;
```

把两个线程的执行任意交错，`(t1, t2)` 只可能是 `01`、`10`、`11`，**`00` 不可能出现**：谁先执行，谁的写入就应该被对方读到。

> **本机实测**（Apple M4，各执行 100 万轮，访存用 relaxed 原子操作）：
>
> | 访存方式 | 00 | 01 | 10 | 11 |
> |---|---|---|---|---|
> | relaxed | **999779** | 111 | 110 | 0 |
> | seq_cst | **0** | 963132 | 36862 | 6 |
>
> "不可能"的 `00` 出现了 99.98%。机器永远是对的，错的是我们的假设。

**原因：现代处理器也是一个（动态的）编译器。**

- 电路把连续的指令拆成更小的 μop，放进一个"池子"
- 每个周期尽可能多地发射 μop：多路发射、乱序执行、按序提交
- 和编译器一样，它也假设"没有别的处理器在干扰"

对 `x` 的写入和对 `y` 的读取是不同地址，交换顺序对单个处理器来说完全无害。写 `x` 时如果 cache miss，处理器会让读 `y` 先完成。于是两个处理器各自先读到了对方的旧值，`00` 就出现了。

这就是**宽松内存模型**（relaxed / weak memory model），目的是让单处理器跑得更快：

- **x86** 的内存模型（x86-TSO）已经是市面上"最强"的了，但仍然允许 store-load 乱序
- **ARM / RISC-V** 更宽松，各个处理器之间的可见性简直像一个分布式系统

### 5. 小结：三个被推翻的假设

| 被推翻的假设 | 原因 | 后面的对策 |
|---|---|---|
| 原子性：一段代码会一口气执行完 | 中断切换；多处理器并行 | 互斥（锁），第 6、7 讲 |
| 顺序：代码按写的顺序执行 | 编译器优化 | compiler barrier、`volatile`、原子操作 |
| 可见性：写入会立刻被所有处理器看到 | 处理器乱序执行、store buffer | 内存屏障（fence）、acquire / release 语义 |

人本质上是"顺序执行的生物"，编程时也只习惯顺序、分支、循环。自己发明的同步方式（ad hoc synchronization）引发过大量系统软件 bug。所以需要**并发控制技术**：不共享内存的部分放心并行，必须共享时，让行为变得"容易理解"。

## Slides 逐页摘要

### 5.1 多处理器编程入门（6 页）

1. 标题页。
2. 操作系统作为"状态机的管理者"引入了共享状态，也就带来了并发。用 model checker 画出两个线程分别打印 A 和 B 的状态图。
3. 线程是共享内存的执行流，有独立的栈和寄存器。简化的线程 API：`spawn(fn)` 创建线程，`join()` 等待所有线程结束。
4. 入门例子：两个线程分别死循环打印 `a` 和 `b`，CPU 使用率超过 100%，操作系统自动把线程放到了不同的处理器上。
5. 追问更多问题：线程真的共享内存吗？怎样证明线程有独立的栈，栈的范围又在哪里？输出混在一起怎么办？创建线程用的是哪个系统调用？能用 gdb 调试吗？
6. `thread.h` 背后是 POSIX Threads（`man 7 pthreads`），可以配置更大的线程栈、detach 等。练习：让线程拥有更大的栈，用 stack probe 验证。

### 5.2 放弃 (1)：原子性（7 页）

1. 标题页。
2. 状态机的隐含假设是"世界上只有一个状态机"，所以读到的一定是自己最后写入的值。共享内存推翻了它：两次读同一个全局变量，结果可能不同。
3. "山寨支付宝"：两个线程并发扣款，余额会下溢，多出花不完的钱。现实中有 Mt. Gox 这样的巨额损失。
4. 游戏里的例子：《暗黑破坏神》（1996）的物品复制 bug，也是一个竞争条件。
5. 求和：两个线程各加 n 次 1，结果可能比 n 还小。直接写汇编指令也不行。
6. "处理器一次执行一条指令"的假设不再成立：单处理器上线程会被中断切走，多处理器上线程本来就在并行执行。历史上，1960 年代大家争相在共享内存上实现互斥，几乎都是错的，直到 Dekker 算法，而它也只能处理两个线程。
7. 那 `printf` 还能在多线程里用吗？它有缓冲区，`buf[pos++] = ch` 不就出问题了？答案在手册里。

### 5.3 放弃 (2)：执行顺序（4 页）

1. 标题页。
2. 求和例子再次出现：加上编译优化后，`-O1` 得到 n，`-O2` 得到 2n。
3. 编译器把内存访问当作"最终一致"来处理，于是共享内存失去了作为线程同步手段的作用。`-O1` 把循环变成"读一次、加 n、写一次"，`-O2` 直接 `sum += n`；`while (!done);` 会被优化成"只读一次然后死循环"。
4. 保证执行顺序的两种方法：插入 compiler barrier（`asm volatile("" ::: "memory")`），或者把变量标成 `volatile`。

### 5.4 放弃 (3)：处理器间的可见性（5 页）

1. 标题页。
2. store-load 例子：两个线程先写自己的变量，再读对方的。模型告诉我们只可能是 01、10、11，但实际运行结果不一样。机器永远是对的，是假设错了。
3. 现代处理器也是动态编译器：把指令拆成 μop，维护一个 μop 池，多路发射、乱序执行、按序提交。它也假设没有别的处理器干扰。
4. 多处理器间内存访问不再即时可见：对不同地址的读写可以交换顺序，甚至在同一个周期完成。写 `x` 时 cache miss，就让读 `y` 先执行。结果两个处理器分别看到 `y = 0` 和 `x = 0`。
5. 宽松内存模型的目的是让单处理器执行更高效。x86 已经是最强的内存模型了，ARM 和 RISC-V 更宽松，像一个分布式系统。推荐 Russ Cox 的 *Hardware Memory Models*。

## 对照：iOS / macOS 上的同一件事

| 课上讲的 | iOS / macOS 中的对应 |
|---|---|
| `thread.h` / pthreads | iOS 同样支持 pthreads；平时更多用 GCD（`DispatchQueue`）和 Swift 的 `Task` |
| 宽松内存模型 | **Apple Silicon 是 ARM 架构，内存模型比 x86 弱得多**，上面的 `00` 就是在 M4 上测出来的。在 x86 模拟器里测不出来的并发 bug，到真机上可能就暴露了 |
| x86-TSO | Rosetta 2 运行 x86 程序时，Apple 芯片会为它切换到硬件 TSO 模式，以保证 x86 程序原有的内存序语义 |
| 检测 data race | Xcode 的 **Thread Sanitizer**（TSan）；Swift 6 的严格并发检查试图在编译期杜绝 data race |
| 多线程下的 `printf` | `NSLog`、`os_log` 都是线程安全的；但 `NSMutableArray` 这类容器不是 |

## 和 xv6 的连接

- xv6 里共享的东西很多：进程表、空闲内存链表、磁盘缓存……每一个都可能被多个 CPU 同时访问，也可能被中断处理程序打断，这一讲的三个问题它全都要面对。
- xv6 的答案在 `kernel/spinlock.c`：用原子指令实现自旋锁，用 `__sync_synchronize()` 插入内存屏障，用 `push_off()` 关中断。下一讲讲完原子指令之后，就能读懂这个文件了。
