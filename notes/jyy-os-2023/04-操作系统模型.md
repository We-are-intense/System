## 这一讲回答的问题

1. 能不能绕开硬件细节，在更高的抽象层次上理解操作系统的行为？

## 核心观点

### 1. 新思路：用 Python 给操作系统建模

前三讲的结论：

- **软件**是状态机，会执行特殊的 syscall 指令请求操作系统，所以操作系统 = 对象 + API
- **硬件**是"无情执行指令的机器"，从 CPU Reset 开始执行固件，所以操作系统 = C 程序

既然都是状态机，理论上只需要两个操作就能观察一切：`dump_state()`（读出当前状态）和 `single_step()`（执行一步）。gdb 就是干这个的，但它的问题是**状态太多、太大**，容易迷失在细节里。

jyy 的解法是**简化**：我们真正关心的只有三件事，应用程序、系统调用、操作系统的内部实现。没人规定它们必须用 C 和真实硬件来实现，所以：

- **应用程序** = 纯计算的 Python 代码 + 系统调用
- **操作系统** = 用 Python 实现的系统调用，配上"假想"的 I/O 设备

### 2. 最小的操作系统玩具：4 个系统调用

| 系统调用 | 作用 |
|---|---|
| `choose(xs)` | 从 `xs` 中随机返回一项（模拟非确定性） |
| `write(s)` | 输出字符串 |
| `spawn(fn)` | 创建一个从 `fn` 开始执行的状态机（线程） |
| `sched()` | 随机切换到任意一个状态机执行 |

除了这 4 个调用，其余代码都是确定性的纯计算。

前三个都很好实现：`write` 就是 `print`，`choose` 就是 `random.choice`，`spawn` 就是把 `fn` 加进可运行列表。**难的是 `sched()`**，它需要：

1. **封存**当前状态机的状态
2. **恢复**另一个已被封存的状态机，让它接着执行

做到这一步，就离真正的分时操作系统只差一步了。

### 3. 用 Python generator 实现"封存"与"恢复"

Python 的 generator 天生就能做这件事：执行到 `yield` 时，整个函数的执行状态（局部变量、执行到哪一行）被冻结在 generator 对象里；之后调用 `send()`，它就从冻结的位置继续执行。

下面是我写的一个说明性例子（不是课程代码）：

```python
import random

def thread(name):
    for i in range(3):
        print(f'{name}{i}')
        yield              # 相当于 sys_sched()：封存自己，交出控制权

runnables = [thread('A'), thread('B')]
while runnables:
    t = random.choice(runnables)   # 调度器：随机挑一个
    try:
        t.send(None)               # 恢复它，执行到下一个 yield
    except StopIteration:
        runnables.remove(t)        # 线程执行完毕
```

每个 generator 就是一个"线程"，外面的循环就是"调度器"。课程的 `os-model.py` 正是用这个机制实现的。

> 我的理解：这是**上下文切换**最干净的模型。在真实的操作系统里，"封存"由中断或 trap 之后的一段汇编完成，它把寄存器保存到内存里；"恢复"就是把另一份保存好的寄存器装回 CPU。xv6 的 `swtch.S` 做的就是这件事。Python generator 帮我们把寄存器、栈这些细节藏了起来，只留下"封存 → 挑一个 → 恢复"的骨架。

### 4. 更完整的模型

在玩具的基础上加入进程、终端和存储，就得到贯穿全课的模型：

| 模型的系统调用 | Linux 中的对应 | 行为 |
|---|---|---|
| `sys_spawn(fn)` | `pthread_create` | 创建共享内存的线程，从 `fn` 开始执行 |
| `sys_fork()` | `fork` | 完整复制当前状态机 |
| `sys_sched()` | 定时被动发生 | 随机切换到某个线程或进程 |
| `sys_choose(xs)` | `rand` | 从 `xs` 中随机选一个 |
| `sys_write(s)` | `printf` | 向终端输出字符串 |
| `sys_bread(k)` | `read` | 读虚拟磁盘第 k 块 |
| `sys_bwrite(k, v)` | `write` | 向虚拟磁盘第 k 块写入 v |
| `sys_sync()` | `sync` | 把写入的数据真正落盘 |
| `sys_crash()` | 长按电源键 | 模拟系统崩溃 |

模型的实现（`mosaic.py`，约 500 行）：

- 进程和线程都是 generator 对象
- 线程共享同一个 `heap`；`fork` 出来的进程得到一份独立的 `heap` 副本
- 程序运行时输出一张**状态图**：顶点是线程和进程的状态、内存快照、设备的输出历史；边是系统调用

**操作系统就是"状态机的管理者"。**

模型做的简化：

- 切换是被动的：程序在任何时刻都可能被调用 `sys_sched()` 切走
- 只有一个终端，没有 `read()`，用 `choose` 代替"可能读到任意值"
- 磁盘是一个 `dict`，可以把任意 key 映射到任意 value；真实磁盘的 key 是整数块号，value 是固定大小（比如 4KB）的数据块

### 5. 建模的意义：把并发 bug 画出来

有了模型，就可以把程序所有可能的执行路径画出来，再和真实操作系统上的运行结果对照。例如经典的并发求和：

```c
void Tsum() {
  for (int i = 0; i < n; i++) {
    int tmp = sum;
    tmp++;        // 假设线程可能在这里被切走
    sum = tmp;
  }
}
```

两个线程各加 n 次，结果却可能小于 2n。在模型里，只要在 `tmp++` 处插入一次 `sys_sched()`，就能在状态图里**看到**丢失更新是怎么发生的。

> 我的理解：这是后面并发几讲（第 5–13 讲）的预告。把"线程可能在任何地方被切走"显式写成 `sys_sched()`，就能看清并发问题的本质：**状态迁移的交错顺序是不确定的**。

### 6. 学习路线：先玩具，后真实系统

**先 100% 理解玩具，再去理解真实系统和玩具的差异。** 玩具的 API 用 C 和 pthread 也能直接实现：`sys_sched` 用随机 `usleep` 模拟，`sys_spawn` 就是 `pthread_create`。玩具并没有脱离真实操作系统，只是暂时把细节放在一边。

## Slides 逐页摘要

### 4.1 理解操作系统的新途径（5 页）

1. 标题页。
2. 回顾：软件是状态机，可以用 syscall 请求操作系统，所以操作系统 = API + 对象；硬件从 CPU Reset 开始执行固件，所以操作系统 = C 程序。
3. 大胆的想法：软件和硬件都是状态机，而状态和迁移是可以"画"出来的。理论上只需要 `dump_state()` 和 `single_step()` 两个操作，gdb 就是做这个的。
4. gdb 的缺陷：状态太多、太大。解决办法是**简化**，把复杂的东西拆成简单的东西，例如只看系统调用（strace）、只看 Makefile 的命令日志。
5. 我们真正关心的是应用程序、系统调用、操作系统内部实现这三者，没人规定它们怎么实现。常规思路是"真实操作系统 + 模拟器"，这门课的思路是"应用 = 纯计算的 Python 代码 + 系统调用，操作系统 = Python 实现的系统调用"。

### 4.2 操作系统"玩具"：设计与实现（6 页）

1. 标题页。
2. 玩具的 4 个 API：`choose`、`write`、`spawn`、`sched`。除此之外的代码都是确定性的纯计算，可以用 list、dict 等数据结构。
3. 一个应用程序示例：随机选 3～5 个线程，每个线程循环 3 次，打印一行后调用 `sys_sched()`。这个程序的执行过程可以画成状态图。
4. 实现系统调用：`write`、`choose`、`spawn` 一目了然，`sched` 却不知道怎么写。它需要封存当前状态机，再恢复另一个。做到这一步，就离分时操作系统只差一步了。
5. 借用 Python 的 generator（无栈协程）：`yield` 封存状态，`send()` 恢复执行并传入返回值，非常适合实现这个玩具（`os-model.py`）。
6. 玩具的意义：没有脱离真实操作系统，只是简化了 API，先不纠结细节。学习路线是先完全理解玩具，再理解真实系统和玩具的差异。玩具的 API 用 C 和 pthread 也能写出来。

### 4.3 建模操作系统（5 页）

1. 标题页。
2. 更全面的模型：进程 + 线程 + 终端 + 存储（包括崩溃一致性），共 9 个系统调用，每个都有 Linux 中的对应。
3. 模型做的简化：切换是被动的、随时可能发生；只有一个终端，没有 `read`；磁盘是一个 `dict`。
4. 模型实现：`mosaic.py` 约 500 行，进程和线程都是 generator，线程共享 `heap`，进程有独立的 `heap` 副本；输出 JSON 格式的状态图，顶点是状态，边是系统调用。操作系统就是"状态机的管理者"。
5. 建模的意义：可以把状态机的执行画出来，直观理解程序执行的全过程，并和真实操作系统的运行结果对照。例子是 `sum` 的并发自增：线程可能在读和写之间被切走。

## 对照：iOS / macOS 上的同一件事

| 模型里的概念 | iOS / macOS 中的对应 |
|---|---|
| generator 的 `yield` / `send` | Swift `async/await` 的挂起点（`await`）和恢复：编译器把函数切成可以挂起和恢复的片段，本质也是"封存状态、稍后恢复" |
| `sys_spawn` | `pthread_create`、`Thread`；GCD 往队列里提交任务，由线程池里的线程执行 |
| `sys_sched` | 由内核调度器决定；用户态没法控制，只能通过 QoS 影响优先级 |
| `sum` 的丢失更新 | Thread Sanitizer（TSan）检测的 data race；Swift 6 严格并发检查想在编译期就杜绝它 |

## 和 xv6 的连接

| 模型 | xv6 |
|---|---|
| generator 对象（一个被封存的状态机） | `struct proc`，其中 `p->context` 保存这个进程内核线程的寄存器 |
| `yield`（封存自己，交出控制权） | `yield()` → `sched()` → `swtch(&p->context, &mycpu()->context)` |
| 外层的调度循环 | `proc.c` 里的 `scheduler()`：遍历进程表，挑一个 `RUNNABLE` 的，`swtch` 过去 |
| `send()`（恢复执行） | `swtch` 把目标进程保存的 `ra`、`sp` 和 callee-saved 寄存器装回 CPU，从它上次停下的地方继续 |
| 被动的 `sys_sched()` | 时钟中断：`usertrap` / `kerneltrap` 发现是时钟中断，就调用 `yield()` |

读 xv6 第 7 章时，可以拿这张表做对照：`swtch.S` 只有二十几行，做的就是 generator 帮我们藏起来的那部分工作。
