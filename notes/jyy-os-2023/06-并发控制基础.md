- 学习计划中的定位：⭐ 必看。从"并发很难"走向"怎样实现互斥"，是理解**锁**的起点

## 这一讲回答的问题

1. 并发程序太难理解，有什么办法让它"回到"顺序执行？（互斥）
2. 只用普通的读和写，能不能实现互斥？（Peterson 算法）
3. 怎样确信一个并发算法是对的？（模型检验）
4. 在真实的多处理器上，硬件和编译器提供了什么来支持互斥？（原子指令、内存屏障）

## 核心观点

### 1. 对策：退回到顺序执行

上一讲的结论是并发程序很难理解。难到什么程度？**验证一个并发执行是否顺序一致，是 NP 完全问题。**

人类的应对办法是**退回到不并发**：标记出一段代码，保证这些代码不会并发执行。这就是**互斥**，被标记的代码叫**临界区**（critical section）。

```c
void Tsum() {
  stop_the_world();     // 其他线程统统停下
  sum++;                // 临界区
  resume_the_world();
}
```

"让世界停下来"真的能做到：

- Java 的垃圾回收就有 stop-the-world 阶段
- **单处理器上，关中断就行**：不会再被切走
- 多处理器上，可以发核间中断让其他处理器停下来

只要程序里能并行的部分足够多，串行化一小段并不会严重拖累性能。

### 2. 失败的尝试：用一个普通变量当锁

```c
retry:
  if (locked != UNLOCK) goto retry;   // ① 检查
  locked = LOCK;                       // ② 上锁
  // 临界区
  locked = UNLOCK;
```

**这和"山寨支付宝"是同一个错误**：①和②之间可能插进另一个线程，两个线程都看到"没上锁"，于是同时进入临界区。**普通的 load 和 store 组合起来不是原子的。**

### 3. Peterson 算法：只用读写实现两个线程的互斥

**前提假设：** 对单个变量的读和写各自是原子的、按顺序完成的。

**厕所隔间的比喻：** A 和 B 争用一个隔间。

1. 想进去之前，先**举起自己的旗子**
2. 在门上贴一张标签，**写上对方的名字**（"让你先"）
3. 如果**对方举着旗，并且门上写的是对方的名字**，就等待；否则进去
4. 出来后**放下自己的旗子**（门上的标签不用管）

```c
// A 的代码（B 对称：x 换成 y，turn 的值换成 A）
while (1) {
  x = 1;                       // 举旗
  turn = B;                    // 门上写"B"
  while (y && turn == B) ;     // 对方举旗、门上又是对方的名字，就等
  /* 临界区 */
  x = 0;                       // 放旗
}
```

**直觉：**

- 只有一个人举旗：他直接进去
- 两个人都举了旗：**门上的标签决定谁进**。两人都往门上写**对方**的名字，后写的覆盖先写的，所以门上最终留下的是**手慢者写下的手快者的名字**。结果是**手快的人进去，手慢的人等待**。

  例如 A 先写 `turn = B`，B 后写 `turn = A`，门上最终是 A。这时 A 检查"B 举旗且门上是 B"，不成立，进入；B 检查"A 举旗且门上是 A"，成立，等待。

但只要想细一点就会发现，各种交错情况非常绕，手工推理很容易漏掉。1960 年代大家提出的互斥算法几乎都是错的，原因就在这里。

### 4. 模型检验：让计算机去枚举

把算法放进第 4 讲的 Python 模型，**每读或写一次共享变量，就插一个 `sys_sched()`**，然后让 model checker 遍历所有可能的执行。状态就是 `(PC₁, PC₂, x, y, turn)` 这个五元组，状态空间很小，计算机几秒钟就能遍历完。

结论：**在顺序一致的内存模型下，Peterson 算法满足 safety**，也就是两个线程永远不会同时进入临界区。而且是在"完全不理解算法"的前提下，"按一下按钮"就证明了。

有了自动遍历，很多问题都能直接回答，只要把它们转成状态图上的搜索问题：

- 出来后把门上的标签撕掉，算法还对吗？在放旗之前撕和之后撕，有区别吗？
- 先贴标签再举旗，还对吗？
- "看对方的旗"和"看门上的标签"这两步交换顺序，还对吗？
- 会不会出现两个人都进不去（**liveness**）？会不会对某一方不公平（**fairness**）？

> 我的理解：jyy 在这里传达的是一种"计算思维"：任何机械的思维活动都可以交给计算机。手工画状态图既慢又容易出错，写一个程序去遍历才是正确的做法。

### 5. 回到现实：模型的假设在多处理器上不成立

模型假设"读写单个变量是原子的、按顺序的"，可上一讲刚证明了：编译器会调换顺序，处理器也会乱序执行。**照着模型直接写 Peterson 算法，在真实机器上是错的。**

> **本机实测**（Apple M4，两个线程各进入临界区 1000 万次，在临界区里对计数器加一）：
>
> | 实现 | 计数结果（期望 20000000） |
> |---|---|
> | 用 relaxed 访存，没有屏障 | **19996485**：互斥被打破，丢了 3515 次更新 |
> | 用 seq_cst 访存（带内存屏障） | **20000000**：正确 |

修正办法：

- **compiler barrier 或 `volatile`**：保证编译器不调换顺序
- **处理器提供的内存屏障指令**：保证处理器之间的可见性顺序

| 平台 | 全屏障指令 |
|---|---|
| x86 | `mfence` |
| ARM | `dmb ish` |
| RISC-V | `fence rw, rw` |

gcc 和 clang 提供的 `__sync_synchronize()` 会生成对应平台的屏障指令，同时也是一个 compiler barrier。

到底哪几个屏障是必不可少的？这已经超出了课程范围。jyy 想传达的是：**除非你对多处理器并发有足够深的理解，否则不要自作聪明写这种并发代码。** 99.9% 的情况下，不碰这些底层行为也能把代码优化好。

另外两个工具建议：

- **测试只能证明"有问题"，不能证明"没问题"**
- 用 [godbolt.org](https://godbolt.org) 看编译器到底生成了什么，不用自己装交叉编译器

### 6. 真正的解法：原子指令

与其费力地用普通读写去拼凑互斥，不如**让硬件直接提供"不可打断、不可乱序"的指令**，也就是**原子指令**，再配合 compiler barrier。

正确的求和：

```c
for (int i = 0; i < N; i++)
  asm volatile("lock incq %0" : "+m"(sum));   // x86：带 lock 前缀的自增
```

`lock` 前缀从 80386 开始引入，最初的实现是锁住总线，保证"读、加一、写回"一次完成，中间不会插入其他处理器的访存。

**acquire / release 语义**是编译器和硬件之间更精细的约定：

- **release**（写）：它**之前**的读写，不能被挪到它**之后**
- **acquire**（读）：它**之后**的读写，不能被挪到它**之前**
- 一对配对的 release 和 acquire：release 之前的所有写入，对 acquire 之后的所有读取都可见

C11 / C++ 的 `std::atomic` 会根据指定的 memory order 自动插入合适的屏障；`fetch_add` 默认是最强的顺序一致（seq_cst）。

> 我的理解：这一讲其实给出了**锁的完整设计思路**。用原子指令保证"检查并上锁"一步完成，用 acquire / release 保证临界区里的读写不会被挪到锁外面。下一讲的自旋锁，就是这两样东西的组合。

## Slides 逐页摘要

### 6.1 互斥问题（8 页）

1. 标题页。
2. 人类是顺序执行的生物，编译优化加上弱内存模型，让并发执行变得极难理解：验证顺序一致性是 NP 完全问题。但人类不轻言放弃，办法是"退回到"顺序执行：标记若干代码块，保证它们按某个顺序执行。
3. 互斥：插入一段"神秘代码"，保证所有被它包住的代码不会并发执行。stop the world 真的可以做到：Java 的 GC、单处理器关中断、多处理器发核间中断。
4. 失败的尝试：用普通变量 `locked` 做锁，先检查再上锁。这和"山寨支付宝"是同一个错误，load 加 store 不是原子的。
5. 更严肃的尝试：先明确假设（读和写各自原子、按顺序），再设计算法。读就像"看一眼字条，刚看完就可能被改"，写就像"闭眼往墙上贴字条，贴完就可能被覆盖"。在模型里，每次读写共享变量后都插入一次 `sys_sched()`。
6. Peterson 算法：A 和 B 争用厕所隔间，举旗、在门上贴对方的名字、对方举旗且门上是对方名字就等待、出来后放旗。
7. 习题：证明 Peterson 正确或给出反例。只有一人举旗时直接进入；两人都举旗时由门上的标签决定。细节情况绕来绕去，很容易漏掉。
8. 手写枚举还是容易错，于是用可执行的状态机模型，对 `(PC₁, PC₂, x, y, turn)` 暴力枚举。页面给出了 C 版本的算法代码。

### 6.2 模型、模型检验与现实（6 页）

1. 标题页。
2. "按一下按钮"的验证：在完全不理解算法的前提下，证明了顺序一致内存模型下 Peterson 算法的 safety。并发编程比想象中难，可以感受一下 Dekker 算法，以及论文 *Myths about the mutual exclusion problem*（1981）。
3. 自动遍历状态空间的乐趣：撕掉标签、调换举旗和贴标签的顺序、调换两次"查看"的顺序，算法还对吗？有没有 liveness 和 fairness 问题？这些都变成了状态图上的遍历问题。
4. Model checker 与自动化：电脑之所以叫电脑，是因为它能替代部分人类思维。手工画状态图无法扩展，任何机械的思维活动都可以用计算机替代，AI 还能替代一部分经验式的决策。
5. 从模型回到现实：原子读写的假设在多处理器上不成立，直接照模型写 Peterson 是错的。修正办法是 compiler barrier 或 `volatile`，加上处理器的屏障指令（x86 `mfence`、ARM `dmb ish`、RISC-V `fence rw, rw`），编译器提供 `__sync_synchronize()`。
6. 维持实现和模型的对应：演示 C 实现的 Peterson。哪些屏障必不可少？测试只能证明有问题，不能证明没问题。推荐用 godbolt.org 看编译器做了什么。

### 6.3 原子指令（4 页）

1. 标题页。
2. 普通变量的读写在编译器和处理器的双重优化下行为复杂。解决办法是由编译器和硬件共同提供不可优化、不可打断的指令：原子指令加上 compiler barrier。
3. 正确的求和：`asm volatile("lock incq %0" : "+m"(sum))`。`lock` 前缀从 80386 开始引入，靠总线控制信号实现。
4. 编译器和硬件的协作：acquire / release 语义。配对的 release-acquire 保证 release 之前的写对 acquire 之后的读可见。`std::atomic` 的 load / store 会根据 memory order 插入屏障，`fetch_add` 保证顺序一致。可以去 godbolt 上试试。

## 对照：iOS / macOS 上的同一件事

| 课上讲的 | iOS / macOS 中的对应 |
|---|---|
| 关中断实现互斥 | 只有内核能做；用户态 App 无法关中断，只能用锁 |
| x86 `lock incq` | Apple Silicon（ARMv8.1 起）用 LSE 原子指令，例如 `ldadd`；更早的 ARM 用 `ldxr` / `stxr` 循环重试 |
| `__sync_synchronize()` / `dmb ish` | C 的 `atomic_thread_fence`；Swift 的 `Atomics` 包（`ManagedAtomic`） |
| acquire / release | `<stdatomic.h>` 的 `memory_order_acquire` / `memory_order_release`；`os_unfair_lock` 等锁的加锁、解锁内部就带有这样的语义 |
| "不要自作聪明写并发代码" | 优先用 `DispatchQueue`（串行队列天然互斥）、`os_unfair_lock`、Swift `actor`；`OSAtomic*` 系列已被弃用 |

## 和 xv6 的连接

现在可以读懂 `kernel/spinlock.c` 的 `acquire()` 了：

```c
push_off();                                        // 关中断（见第 14 讲）
while (__sync_lock_test_and_set(&lk->locked, 1) != 0)
  ;                                                // 原子交换：检查并上锁一步完成
__sync_synchronize();                              // 内存屏障：临界区的访存不能挪到锁外
```

- `__sync_lock_test_and_set` 在 RISC-V 上编译成原子交换指令 `amoswap`，正是 6.3 讲的"原子指令"，解决了 6.1 里"检查和上锁之间被插队"的问题
- `__sync_synchronize()` 编译成 `fence`，正是 6.2 讲的内存屏障
- `release()` 里也有一个 `__sync_synchronize()`，作用是让临界区内的写入，在锁被释放之前对其他 CPU 可见
